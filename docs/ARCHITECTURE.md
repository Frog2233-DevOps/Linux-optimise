# Архитектура

Один файл, три режима. Общее ядро:

- `preflight` — только чтение: ОС, root, место, host-ключи, определение текущих портов SSH.
- `apply` — транзакционное применение. Порядок выбран так, чтобы ни один шаг не отнимал доступ раньше, чем появится замена.
- `verify` — набор идемпотентных проверок против `/var/lib/bootstrap/state.env`, код 3 при дрейфе.

## Модель безопасности применения

1. **Транзакция SSH.** Перед правкой drop-in снимается копия. Любой сбой до `SSH_TXN=0` откатывает конфиг sshd и правила ufw, добавленные транзакцией, и перезапускает ssh.
2. **Два порта.** UFW открывает старый и новый порт. Старый закрывается только по `--close-old-ports` и только при нулевом числе провалов проверок.
3. **Проверка эффективного конфига.** После записи drop-in сравнивается `sshd -T` — если другой файл перебил значения, идёт откат.
4. **Ключ до пароля.** `PasswordAuthentication no` ставится только при непустом `authorized_keys`, а `sudo -n` проверяется на месте.
5. **Подтверждение.** Интерактивно печатаются отпечатки ключей и запрашивается `y`; `--yes` для автоматики.

## Точки отказа

- cloud-init перезаписывает `sshd_config.d` и `PasswordAuthentication` после ребута → `99-bootstrap.cfg` с `ssh_pwauth: false`.
- cloud firewall провайдера не виден ufw → предупреждение в конце каждого apply.
- `fail2ban` на 24.04 требует `noble-updates` → версия проверяется и деградирует в warn, apply не падает.
